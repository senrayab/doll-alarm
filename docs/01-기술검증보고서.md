## 0. 결론 요약

| 항목 | 판정 | 한 줄 요약 |
|---|---|---|
| 나나코어 대기 순번 감시 | **가능 (실호출 확인 완료)** | 공개 뷰어가 Supabase 공개(anon) API로 명단을 읽는다. 서버(Worker)도 같은 방식으로 읽을 수 있다. |
| 베베픽 대기열 감시 | **불가 — 자동 감시하지 않음** | 로그인 필수 + robots.txt가 주문 화면 자동 접근 금지 + 약관에 "자동 수집(크롤링) 금지" 명시. 바로가기만 제공. |
| 앱 종료·화면 꺼짐 상태 알림 | **가능** | 감시는 서버(Cloudflare)에서, 알림은 Web Push로. 휴대폰은 아무것도 실행할 필요 없음. |
| PWA만으로 백그라운드 감시 | **불가** | 모바일 브라우저는 종료된 웹앱의 주기 실행을 허용하지 않는다. |
| 5초 주기 | **제공하지 않음** | 나나코어 자체 화면도 15초마다 갱신. 최소 15초부터 제공. |
| 로그인 필요한 사용자 지정 사이트 | **자동 감시 불가** | 서버로 쿠키를 보내지 않는 원칙과 양립 불가. "감시 불가 — 로그인 필요"로 표시. |
| 공개 페이지 사용자 지정 사이트 | **부분 가능** | 서버에서 HTML을 받아 키워드·가격 패턴 검사. JS로만 그려지는 사이트는 불가. |
| 서버에 개인정보 미저장 | **가능** | 닉네임도 평문 대신 해시로 저장 (3장). |

## 1. 전체 시스템 아키텍처

```
[휴대폰 PWA]                               [Cloudflare Worker 1개]
 ├ IndexedDB: 사이트·감시 설정·닉네임·알림내역   ├ 정적 파일 제공 (PWA 화면)
 ├ Service Worker: 푸시 수신 → 알림 표시        ├ /api/jobs  감시 작업 등록·수정·삭제
 │                 + 알림 내역 IndexedDB 저장   ├ Durable Object (작업 1개당 1개)
 └ 감시 등록 시 서버로 보내는 것:                │    ├ 알람으로 15초~5분마다 깨어남
     · 푸시 구독 정보                           │    ├ 공개 데이터 조회 → 이전 상태와 비교
     · 사이트 모듈 ID (예: nanacore)            │    └ 조건 충족 시 Web Push 발송
     · 닉네임 해시 (평문 X)                      └ VAPID 개인키 (Worker secret)
     · 알림 조건·주기·예약 시간                          │
                                                        ▼
                         [푸시 서비스: FCM(안드로이드) / APNs(아이폰)] → 휴대폰 시스템 알림
```

### 기획서와 다르게 제안하는 점

1. **Cloudflare Pages + Workers → Worker 하나로 통합.** 지금은 Worker 하나가 정적 파일(Static Assets)과 API, Durable Object를 함께 제공할 수 있다. 배포 단위가 하나라 관리가 쉽다.
2. **Cron Triggers → Durable Object 알람.** Cron의 최소 간격은 1분이다. 15초·30초 주기는 Durable Object의 `alarm()`으로만 구현할 수 있다. 감시 작업마다 자기 주기와 예약 시간을 따로 가지므로 구조도 더 단순하다. Cron은 "멈춘 작업 정리" 같은 하루 1회 청소용으로만 쓴다.
3. **Next.js → Vite + React + TypeScript.** 서버 렌더링이 필요 없는 순수 클라이언트 PWA라서 Next.js의 이점이 거의 없다. Vite가 빌드가 가볍고 PWA 플러그인 연동이 간단하다. (Next.js를 꼭 원하면 static export로도 가능하다.)

## 2. 사이트별 검증

### 2-1. 나나코어 — 자동 감시 가능

**확인한 사실** (`https://nanacore-queue.netlify.app/?view=viewer` 페이지 소스 분석)

- 정적 HTML 하나에 스크립트가 들어 있고, 데이터는 **Supabase**(`loaniqinvzbfofigryll.supabase.co`)에서 읽는다.
- 페이지에 **공개용 anon 키**가 들어 있다. 소스 주석에도 "service_role 키는 절대 넣지 마세요"라고 적혀 있어, 이 키가 공개용임을 운영자가 의도했다.
- 뷰어는 로그인 없이 다음 쿼리로 명단을 읽는다.
  ```
  queue_items: select id, position, nickname, order_detail, status  order by position
  ```
- 자체 화면도 **15초마다 다시 읽고**(`setInterval(load,15000)`), Supabase Realtime(`postgres_changes`)으로 변경을 실시간 구독한다.
- `status` 값: `current`(진행 중), `pending`(대기), `done`(완료), `skipped`(건너뜀)
- 방송 종료 시 관리자가 명단을 비운다(`queue_start_new_day`). 이때 내 정보가 "사라짐" 상태가 된다.
- `robots.txt`가 없다(404). 별도 접근 제한이 없다.

**감시 방식**

Worker가 Supabase REST(`/rest/v1/queue_items?select=...`)를 anon 키로 GET한다. 뷰어 페이지와 똑같은 공개 읽기다.

| 판정 | 계산 |
|---|---|
| 내 순번 | 닉네임이 일치하는 행의 `position` |
| 내 앞 인원 | `current` 1명 + 내 `position`보다 작은 `pending` 수 |
| 내 차례 도달 | 내 행의 `status === 'current'` |
| 완료 | 내 행이 `done` |
| 사라짐 | 직전 확인에는 있었는데 이번에 없음 (명단 비움 포함) |
| 감시 오류 | HTTP 오류, 응답 형식 변경, 필드 누락 → **"순번 도달"과 절대 혼동하지 않음** |

같은 닉네임이 여러 행이면(주문 여러 건) 가장 앞의 미완료 행을 기준으로 삼는다.

**실호출 확인 (2026-11-16)**

사용자 PC에서 anon 키로 `queue_items?select=position,status&order=position.asc&limit=5`를 호출했다. 로그인 없이 `[{"position":1,"status":"done"}, …]` 형태로 응답이 왔다. 서버 감시 방식 사용 가능.

**리스크**: 운영자가 테이블 구조나 접근 권한(RLS)을 바꾸면 감시가 깨진다. 이 경우 "감시 오류"로 표시하고 알림 1회를 보낸다.

### 2-2. 베베픽 — 자동 감시하지 않음

**확인한 사실**

- 주문·대기열 화면(`/live`, `/plus`)은 **구글(유튜브) 로그인 필수**다. 로그인 정보는 브라우저 localStorage의 Supabase 인증 토큰에 저장된다.
- `robots.txt`: 첫 화면과 약관 외 **전체 `Disallow`**. AI 에이전트·자동 수집기도 명시적으로 차단한다.
- 사이트 바닥글: **"자동 수집(크롤링) … 이용을 금지합니다."**
- `x-frame-options: DENY`라서 우리 앱 안에 iframe으로 띄울 수도 없다.

**기획서의 검증 질문에 대한 답**

| 질문 | 답 |
|---|---|
| 1. 로그인 상태에서 대기열 정보를 읽을 수 있는가? | 사람이 브라우저로는 가능. 우리 앱이 읽는 것은 불가 (다른 출처 DOM·localStorage 접근 불가, iframe 금지). |
| 2. 사용자 기기에서만 로그인 세션을 활용할 수 있는가? | 웹앱으로는 불가. 다른 사이트의 세션은 그 사이트 출처에 묶여 있다. |
| 3. 백그라운드에서 실행할 수 있는가? | 불가. |
| 4. 앱 종료 후 감시할 수 있는가? | 서버로 토큰을 보내야만 가능 → 원칙 위반이라 불가. |
| 5. 사이트 정책에 위배되지 않는가? | **위배된다.** robots.txt와 약관 모두 자동 수집 금지. |

**결론**: 베베픽은 "지원 불가 사이트"로 등록한다. 앱에서는 **바로가기 + 수동 체크 리마인더**(예: 지정 시간에 "베베픽 순서 확인해 보세요" 푸시)만 제공한다. 공식 알림 기능이나 API가 필요하면 운영자에게 문의하는 것이 유일한 정식 경로다.

### 2-3. 사용자 지정 사이트

| 사이트 상태 | 지원 범위 |
|---|---|
| 공개 HTML에 데이터가 있음 | 서버에서 HTML 조회 → 키워드 포함 여부, 가격 패턴, 페이지 변경 감지 |
| JS로만 그려짐 (SPA) | 서버 HTML에 데이터가 없음 → "자동 감시 불가 — 전용 모듈 필요" |
| 로그인 필요 | "자동 감시 불가 — 로그인 필요" |
| robots.txt가 해당 경로 금지 | 등록 시 경고, 자동 감시 불가 |

"연결 확인" 버튼은 서버가 URL을 한 번 조회해서 HTTP 상태, robots.txt 허용 여부, HTML 안의 텍스트 양을 보고 위 4가지 중 하나로 판정한다. 지원하지 않는 기능을 정상인 것처럼 보이지 않게 한다.

## 3. 개인정보가 서버로 가지 않는 구조

| 데이터 | 위치 | 비고 |
|---|---|---|
| 사이트 로그인 정보·세션 | 해당 사이트의 브라우저 저장소 | 우리 앱이 건드리지 않음 |
| 사이트 목록·감시 설정·닉네임(평문)·알림 내역 | 휴대폰 IndexedDB | |
| 닉네임 | 서버에는 **`SHA-256(작업별 salt + 정규화한 닉네임)`** | 서버가 명단 각 행을 같은 방식으로 해시해 비교 |
| 푸시 구독(endpoint, keys) | 서버 Durable Object | 보호 대상. 로그에 남기지 않음 |
| 작업 상태(마지막 순번, 마지막 알림) | 서버 Durable Object | 중복 알림 방지용 최소 정보 |
| 작업 삭제 토큰 | 휴대폰 + 서버(해시) | 계정 없이 "내 작업"만 지울 수 있게 하는 무작위 비밀값 |

- 나나코어 명단은 공개 정보다. 그래서 닉네임 해시는 "누가 무엇을 감시하는지"를 서버 DB에 평문으로 남기지 않는 용도다. 완전한 익명화는 아니다.
- 알림 문구에는 닉네임을 넣지 않는다 ("대기 순번이 15번으로 변경되었습니다"). 푸시 내용은 브라우저 푸시 표준(RFC 8291)으로 암호화되어 FCM·APNs도 볼 수 없다.
- 감시 중지·삭제 시 Durable Object 저장소를 통째로 지운다 (`deleteAll`).
- 푸시 서비스가 410(구독 만료)을 돌려주면 작업을 자동 삭제한다.

## 4. 모바일 백그라운드·푸시 알림 한계

| 항목 | 안드로이드 (Chrome) | 아이폰 (Safari) |
|---|---|---|
| 웹 푸시 수신 | 가능 | **iOS 16.4 이상 + 홈 화면에 추가한 PWA에서만** 가능 |
| 앱 종료·화면 잠금 상태 수신 | 가능 | 가능 |
| 알림 권한 요청 | 아무 때나 | **버튼 탭(사용자 동작) 안에서만** |
| PWA 자체 백그라운드 주기 실행 | Periodic Background Sync는 최소 약 12시간, 보장 없음 → 사용 불가 | 지원 안 함 |
| 배터리 절약 모드 | 알림 지연 가능 | 집중 모드에서 숨겨질 수 있음 |

- **서버 감시 + 푸시 구조에서는 휴대폰 배터리를 거의 쓰지 않는다.** 화면은 열려 있을 때만 갱신한다.
- 푸시 발송 시 `Urgency: high`, 짧은 `TTL`(예: 5분)을 지정한다. 늦게 도착한 "내 차례" 알림은 의미가 없기 때문이다.
- **"완성" 판정 기준**: 실제 휴대폰을 잠근 채로, 앱을 종료한 상태에서 순번 변경 알림을 받는 것을 확인해야 한다. (기획서 원칙 그대로)

## 5. Cloudflare 실행 주기·비용

※ 아래 한도는 작성 시점 기준 알려진 값이다. 배포 전에 Cloudflare 요금 페이지에서 다시 확인한다.

| 항목 | 무료(Workers Free) | 유료(Workers Paid, 월 $5) |
|---|---|---|
| Worker 요청 | 하루 10만 건 | 월 1천만 건 포함 |
| Worker CPU 시간 | 호출당 10ms | 호출당 최대 30초 (기본) |
| Durable Object (SQLite) | 무료 플랜에서 사용 가능, 하루 10만 요청 | 포함량 넉넉함 |
| Cron 최소 간격 | 1분 | 1분 |

**사용량 계산 (감시 작업 1개 기준)**

| 주기 | 하루 호출 수 (24시간 내내) | 방송 시간 4시간만 예약 |
|---|---|---|
| 15초 | 5,760 | 960 |
| 30초 | 2,880 | 480 |
| 1분 | 1,440 | 240 |

개인용으로 작업 몇 개 수준이면 무료 한도로 충분하다.

**리스크**: 푸시 발송 시 암호화(ECDH + AES-GCM)와 VAPID 서명(ECDSA)이 필요하다. 무료 플랜의 10ms CPU 한도에 걸릴 수 있다. WebCrypto는 네이티브라 대부분 통과하겠지만, 4단계에서 실측하고 초과하면 유료 플랜($5)을 권장한다.

**감시 주기 선택지**: `15초 / 30초 / 1분 / 3분 / 5분` (5초·10초는 제공하지 않음 — 대상 사이트 자체 갱신이 15초)

## 6. 불가능하거나 위험한 부분 (명시)

1. **베베픽 자동 감시** — 정책 위반이라 구현하지 않는다.
2. **로그인 필요 사이트의 자동 감시** — 서버 쿠키 전송 금지 원칙상 불가.
3. **PWA 단독 백그라운드 감시** — 모바일 OS가 허용하지 않는다.
4. **15초 미만 주기** — 대상 사이트 부담. 제공하지 않는다.
5. **나나코어 구조 변경** — 사전 예고 없이 깨질 수 있다. 오류 감지·알림으로 대응한다.
6. **아이폰 구버전(16.4 미만)·홈 화면 미추가** — 푸시를 받을 수 없다. 앱에서 안내한다.
7. **JS 렌더링 쇼핑몰** — 서버 HTML 파싱으로는 상품 정보를 못 읽는다. Cloudflare Browser Rendering(유료)이나 사이트별 공개 API가 필요하다. MVP 범위 밖이다.
